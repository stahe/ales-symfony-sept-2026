    8. Autenticación y autorización

    Para cada solicitud surgen dos preguntas distintas:

    • ¿Quién es el usuario? Esto es la autenticación: el usuario se ha identificado con un nombre de usuario y una contraseña, y cada solicitud posterior debe demostrar que proviene de él;
    • ¿Tiene permiso para acceder a esta página? Esto es la autorización: en el caso de estudio, solo un usuario con el rol ADMIN administra los médicos y los clientes.

    La prueba de identidad debe incluirse en cada solicitud. [Symfony] normalmente almacena al usuario conectado en su sesión (véase la sección sobre los ámbitos), que es la solución más simple para una aplicación web. En cambio, el caso de estudio, en todas sus versiones ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel]), utiliza un token (JWT, JSON Web Token), que usaremos aquí: después del inicio de sesión, el servidor genera un token que contiene la identidad del usuario y lo firma con una clave secreta (este es el principio de la cookie firmada del Ejemplo 23). El token se almacena en una cookie; el navegador la reenvía con cada solicitud; el servidor verifica la firma. El usuario puede leer su token, pero no modificarlo: cualquier modificación invalida la firma. El formato está estandarizado (RFC 7519), lo entienden todos los lenguajes de programación y el token incluye su fecha de expiración. Lo más importante es que el servidor no necesita almacenar nada: cualquier servidor que conozca la clave puede verificar el token.

    [Symfony] tiene un componente de seguridad completo, integrado por SecurityBundle, cuyos elementos usaremos tal cual:

    • las URL de la aplicación se distribuyen entre cortafuegos (firewalls), cada uno con su propio método de autenticación de usuarios;
    • la autenticación está a cargo de los autenticadores (authenticators): objetos que determinan la identidad del usuario en cada solicitud. [Symfony] proporciona varios (formulario de inicio de sesión, sesión, token de API, etc.); escribiremos el nuestro, que lee el token JWT. El resto de la aplicación solo ve el resultado: el usuario autenticado, proporcionado por [#[CurrentUser]], [$this->getUser()] y, en las vistas, [app.user];
    • los usuarios los proporciona un proveedor de usuarios, y sus contraseñas se procesan con hash mediante el componente PasswordHasher (algoritmo [bcrypt]);
    • las autorizaciones se basan en roles: la protección de las páginas se describe mediante reglas de control de acceso ([access_control]) o mediante el atributo [#[IsGranted]] de las acciones; las vistas comprueban un derecho mediante [is_granted];
    • Los intentos de inicio de sesión están limitados por el componente RateLimiter (Ejemplo 27).

    Todo esto lo realizan los listeners de eventos del kernel (capítulo anterior): el cortafuegos escucha [kernel.request] (prioridad 8), [#[IsGranted]] se lee en [kernel.controller_arguments] y las denegaciones de acceso son excepciones, gestionadas en [kernel.exception].

    La generación y la verificación de tokens las realiza la biblioteca [firebase/php-jwt], la más utilizada en [PHP], instalada por el archivo [composer.json] de los ejemplos. (Existe un bundle muy utilizado para tokens —JWT y [LexikJWTAuthenticationBundle]— diseñado para API; para una aplicación web bastan unas pocas líneas, que ilustran mejor el mecanismo.)

    8.1.1. Configuración: .env, bundles.php y framework.yaml

    El token se firma con una clave secreta, que no debe estar codificada en el código. Es hora de separar realmente la configuración del código. Los ajustes específicos de una instalación están en el archivo [.env] (Ejemplo 01), que ahora contiene tres líneas nuevas (un comentario, seguido de dos variables):

APP_ENV=dev
APP_SECRET=6144ddf9f821deebee2291ab7742d7a9
# la clave que firma los tokens JWT (al menos 32 caracteres), y su duración
JWT_SECRET=a-secret-key-of-at-least-32-characters-for-example-25
JWT_DURATION_MINUTES=60

    El estándar exige que el algoritmo utilizado (HMAC-SHA256) tenga una clave de al menos 256 bits, es decir, 32 bytes; la biblioteca rechaza cualquier clave más corta. El código en sí no lee directamente el archivo [.env]: el componente [Dotenv] (ejemplo 01) lo ha convertido en variables de entorno, que el contenedor proporciona a los servicios que las solicitan (lo veremos con el servicio [AuthService]). Una variable de entorno real tiene prioridad sobre el archivo [.env]: en [Linux] o [macOS], la aplicación se iniciaría con una clave diferente de la siguiente manera:

    1
    JWT_SECRET="another-key-of-at-least-thirty-two-characters" php -d variables_order=EGPCS -S localhost:8000 -t public

    y en [Windows] (PowerShell):

    1
2
    $env:JWT_SECRET="another-key-of-at-least-thirty-two-characters"
php -d variables_order=EGPCS -S localhost:8000 -t public

    (La opción [-d variables_order=EGPCS] indica a [PHP] que llene el arreglo [$_ENV] con las variables de entorno, lo que su configuración predeterminada no siempre hace.) En producción, los secretos suelen confiarse a la bóveda de [Symfony] (secrets vault, comando [bin/console secrets:set]), que los almacena cifrados dentro del proyecto.

namespace App\Security;

use Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface;
use Symfony\Component\Security\Core\User\UserInterface;

readonly class User implements UserInterface, PasswordAuthenticatedUserInterface
{
    public function __construct(
        public string $login,
        public string $name,
        // el rol: USER o ADMIN
        public string $role,
        // el HASH de la contraseña (vacío para un usuario leído a partir de un token)

    public function getRoles(): array
    {
        return ['ROLE_'.$this->role];

    public function getPassword(): string
    {
        return $this->passwordHash;
    }

Para verificar una contraseña ingresada, se calcula su hash y se compara con el almacenado;

// src/Security/UsersService.php: los usuarios, en memoria (el ejemplo 28
// y el caso de estudio los pondrán en una base de datos). UserProviderInterface: un
// PROVEEDOR de usuarios, en el sentido de Symfony (véase config/packages/security.yaml)

namespace App\Security;

use Symfony\Component\Security\Core\Exception\UnsupportedUserException;
use Symfony\Component\Security\Core\Exception\UserNotFoundException;
use Symfony\Component\Security\Core\User\UserInterface;
use Symfony\Component\Security\Core\User\UserProviderInterface;

class UsersService implements UserProviderInterface
{
    // NUNCA guardamos una contraseña, solo su hash bcrypt, calculado
    // una vez por todas con: php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const USERS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],
        'admin' => ['Administrator', 'ADMIN', '$2y$10$m5o9euCi0EdgoZkLVw.UsO58RxJcqhMBfVrlLMCIOh2LyGSjuN29K'],
    ];

    public function find(string $login): ?User
    {
        if (! isset(self::USERS[$login])) {
            return null;
        }
        [$name, $role, $hash] = self::USERS[$login];
        return new User($login, $name, $role, $hash);
    }

    // los tres métodos de UserProviderInterface
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        return $this->find($identifier) ?? throw new UserNotFoundException();
    }

    // el usuario almacenado en la sesión, por recargar: nunca se invoca aquí,
    // ya que el firewall es stateless
    public function refreshUser(UserInterface $user): UserInterface
    {
        throw new UnsupportedUserException();
    }

    public function supportsClass(string $class): bool
    {
        return $class === User::class;
    }
}
    • Líneas 17–20: dos usuarios de prueba, definidos directamente en el código (el ejemplo 28 y el caso de estudio los almacenarán en una base de datos): para cada inicio de sesión, el nombre, el rol y el hash de la contraseña. El hash se genera con el algoritmo bcrypt, diseñado para contraseñas. Tiene dos características distintivas. Es deliberadamente lento, con un nivel de lentitud ajustable (el costo, aquí fijado en 10: 2^10 ciclos de cálculo, lo que da como resultado el hash [$10$]): unas pocas decenas de milisegundos, imperceptibles para un usuario, pero que hacen muy costoso para un atacante probar miles de millones de contraseñas. Es con sal: una sal generada aleatoriamente se mezcla con la contraseña antes de aplicar el hash y se almacena dentro del propio hash (los 22 caracteres que siguen a [$10$]); así, dos usuarios con la misma contraseña tendrán hashes diferentes. Los hashes se calcularon una vez por todas con la función [password_hash] de [PHP] (línea 16), o con el comando [bin/console security:hash-password] de [Symfony]: calcularlos en cada solicitud sería una pérdida de tiempo innecesaria, ya que la aplicación se reconstruye con cada solicitud. [bcrypt] solo tiene en cuenta los primeros 72 bytes de una contraseña: el caso de estudio lo tiene en cuenta;
    • líneas 22–29: el usuario de un inicio de sesión, o [null]. [isset] verifica la existencia de una clave; la asignación [[$name, $role, $hash] = ...] desestructura un arreglo: cada variable recibe el elemento correspondiente;
    • líneas 32–47: los tres métodos de la interfaz [UserProviderInterface], que convierten la clase en un proveedor de usuarios: [loadUserByIdentifier] devuelve el usuario asociado a un identificador, o lanza la excepción [UserNotFoundException]; [refreshUser] recarga el usuario almacenado en la sesión (innecesario con un firewall sin estado); [supportsClass] especifica la clase de los usuarios proporcionados. El operador [??] seguido de [throw] lanza la excepción cuando la expresión del lado izquierdo se evalúa como [null].

    <?php
// src/Security/AuthService.php: la verificación de las contraseñas y de los tokens JWT

namespace App\Security;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;
use Throwable;

class AuthService
{
    // el nombre de la cookie que lleva el token
    public const COOKIE = 'token';

    public function __construct(
        private UsersService $users,
        // el servicio de hash de contraseñas (véase config/packages/security.yaml)
        private UserPasswordHasherInterface $hasher,
        // #[Autowire(env: ...)]: el valor de una variable de entorno (archivo .env);
        // el prefijo int: lo convierte en un entero
        #[Autowire(env: 'JWT_SECRET')] private string $secret,
        #[Autowire(env: 'int:JWT_DURATION_MINUTES')] public readonly int $durationMinutes,
    ) {
    }

    // el usuario, o null si el login es desconocido o la contraseña es incorrecta.
    // isPasswordValid aplica el hash a la contraseña ingresada con la sal del hash almacenado,
    // y luego compara los dos resultados
    public function validate(?string $login, ?string $password): ?User
    {
        if (! $login || $password === null) {
            return null;
        }
        $user = $this->users->find($login);
        if ($user === null || ! $this->hasher->isPasswordValid($user, $password)) {
            return null;
        }
        return $user;
    }

    // el token JWT del usuario, firmado con la clave secreta (HMAC-SHA256)
    public function createToken(User $user): string
    {
        $now = time();
        // el contenido del token: los "claims" (afirmaciones sobre el usuario)
        $claims = [
            'sub' => $user->login,
            'name' => $user->name,
            'role' => $user->role,
            'iat' => $now,
            'exp' => $now + $this->durationMinutes * 60,
        ];
        return JWT::encode($claims, $this->secret, 'HS256');
    }

    // el usuario descrito por un token cuya firma y fecha de expiración
    // son válidas; null en caso contrario (token falsificado, expirado o ilegible)
    public function check(string $token): ?User
    {
        try {
            // decode devuelve un objeto; (array) lo convierte en un arreglo asociativo
            $claims = (array) JWT::decode($token, new Key($this->secret, 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new User($claims['sub'], $claims['name'], $claims['role'], claims: $claims);
    }
}
    • Líneas 17–26: el servicio recibe el proveedor de usuarios, el servicio de hash de contraseñas ([UserPasswordHasherInterface], que aplica el algoritmo seleccionado en [security.yaml]) y dos valores de configuración. El atributo [#[Autowire(env: 'NAME')]] proporciona el valor de una variable de entorno; un prefijo lo convierte: [int:] a entero (hay otros: [bool:], [json:], [base64:]...). La duración de vida es una propiedad pública de solo lectura: el controlador la usará;
    • líneas 31–41: verificación de un nombre de usuario y una contraseña. [isPasswordValid] calcula el hash de la contraseña ingresada usando la sal del hash almacenado y compara los dos hashes. Un nombre de usuario desconocido y una contraseña incorrecta producen el mismo resultado, [null];
    • Líneas 44–56: generación del token. El token contiene un arreglo de afirmaciones (claims) sobre el usuario. Algunas tienen nombres estandarizados: [sub] (subject), el identificador del usuario; [iat] (issued at), la fecha de creación; [exp] (expiration), la fecha de expiración. Las fechas se expresan en segundos transcurridos desde el 1 de enero de 1970 (la función [time()] de [PHP]). Los demás campos son opcionales: aquí, el nombre y el rol. [JWT::encode] genera el token y lo firma con el algoritmo [HS256] (HMAC-SHA256, una firma con una clave secreta compartida);
    • líneas 60–69: verificación del token. [JWT::decode] verifica la firma y la fecha de expiración, y luego devuelve las afirmaciones (un objeto, convertido en arreglo mediante [(array)]). Cualquier anomalía (token falsificado, expirado o mal formado) lanza una excepción; [catch (Throwable)] las captura todas ([Throwable] es la interfaz de todas las excepciones y errores de [PHP]; el nombre de la variable es opcional cuando no se usa). // src/Security/TokenAuthenticator.php: el AUTENTICADOR del firewall (véase
// config/packages/security.yaml): en cada solicitud, establece quién es el usuario,
// a partir del token JWT de la cookie [token]

namespace App\Security;

use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Exception\AuthenticationException;
use Symfony\Component\Security\Core\Exception\CustomUserMessageAuthenticationException;
use Symfony\Component\Security\Http\Authenticator\AbstractAuthenticator;
use Symfony\Component\Security\Http\Authenticator\Passport\Badge\UserBadge;
use Symfony\Component\Security\Http\Authenticator\Passport\Passport;
use Symfony\Component\Security\Http\Authenticator\Passport\SelfValidatingPassport;
use Symfony\Component\Security\Http\EntryPoint\AuthenticationEntryPointInterface;

class TokenAuthenticator extends AbstractAuthenticator implements AuthenticationEntryPointInterface
{
    public function __construct(private AuthService $auth)
    {
    }

    // el autenticador actúa solo si la solicitud lleva la cookie del token;
    // de lo contrario, el visitante permanece anónimo
    public function supports(Request $request): ?bool
    {
        return $request->cookies->has(AuthService::COOKIE);
    }

    // el PASAPORTE del usuario: quién es (la credencial), y cómo verificarlo.
    // El token ya fue verificado: el pasaporte se valida a sí mismo (SelfValidatingPassport)
    public function authenticate(Request $request): Passport
    {
        $user = $this->auth->check($request->cookies->get(AuthService::COOKIE));
        if ($user === null) {
            throw new CustomUserMessageAuthenticationException('invalid token');
        }
        // la credencial: el login, y una función que devuelve al usuario (aquí, el del
        // token, sin consultar la lista de usuarios)
        return new SelfValidatingPassport(new UserBadge($user->login, fn () => $user));
    }

    // un token válido: null, la solicitud continúa su camino hacia la acción
    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null;
    }

    // un token inválido (expirado, falsificado): se envía a /login, y eliminamos la cookie
    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        $response = new RedirectResponse('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // el PUNTO DE ENTRADA: la respuesta dada a un visitante anónimo que solicita una
    // página protegida; aquí, una redirección a la página de inicio de sesión
    public function start(Request $request, ?AuthenticationException $authException = null): Response
    {
        return new RedirectResponse('/login');
    }
}

    Para cada solicitud que pasa por el firewall, [Symfony] llama a los métodos del autenticador en este orden:

    • líneas 28–31: [supports]: ¿participa el autenticador en esta solicitud? Sí, si contiene la cookie del token. De lo contrario, no ocurre nada: el visitante sigue siendo anónimo;
    • líneas 35–44: [authenticate] construye un pasaporte: la identidad del usuario (una credencial, [UserBadge]) y las credenciales que se deben verificar. Un formulario de inicio de sesión estándar incluiría la contraseña ingresada en el pasaporte, que [Symfony] verificaría por sí mismo. Aquí, la prueba es el token, ya verificado por [AuthService]: el pasaporte se valida a sí mismo ([SelfValidatingPassport]). La credencial contiene el inicio de sesión y una función que identifica al usuario: en este caso, el usuario descrito por el token, sin consultar la lista de usuarios (sin esta función, [Symfony] solicitaría el usuario al proveedor). Un token no válido lanza una excepción de autenticación;
    • líneas 47–50: [onAuthenticationSuccess]: la autenticación se realizó con éxito. Devolver [null] permite que la solicitud llegue a la acción con un usuario autenticado. (Un formulario de inicio de sesión redirigiría aquí a la página de inicio);
    • líneas 53–58: [onAuthenticationFailure]: la autenticación falló (token expirado o falsificado). La respuesta redirige a la página de inicio de sesión y aprovecha para borrar la cookie: [clearCookie] agrega a la respuesta una cookie vacía y ya expirada;
    • líneas 62–65: [start] es el método de la interfaz [AuthenticationEntryPointInterface]: el punto de entrada del firewall, es decir, la respuesta enviada a un visitante anónimo que solicita una página protegida. En este caso, una redirección a la página de inicio de sesión.

    El autenticador no deniega el acceso: determina quién es el usuario, o determina que el usuario es anónimo. Esto es la autenticación. Las denegaciones son responsabilidad del control de acceso.

namespace App\Controller;

use App\Security\AuthService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    public function __construct(private AuthService $auth)
    {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->render('auth/login.html.twig');
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        // el token anti-CSRF del formulario (véase el ejemplo 21)
        if (! $this->isCsrfTokenValid('login', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $request->getPayload()->getString('login');
        $user = $this->auth->validate($login, $request->getPayload()->getString('password'));
        if ($user === null) {
            // un mensaje deliberadamente vago: no decimos si es el login o la contraseña
            return $this->render('auth/login.html.twig', ['login' => $login,
                'error' => 'Incorrect login or password.']);
        }
        // el token, en una cookie: el JavaScript de la página no puede leerlo
        // (httpOnly); no viaja con las solicitudes POST provenientes de otros sitios
        // (sameSite); desaparece al mismo tiempo que expira el token
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    // cierre de sesión: solo POST (un simple enlace, colocado en otro sitio, no puede
    // cerrar la sesión del usuario sin que se entere); eliminamos la cookie
    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }
}
    • líneas 36–38: el formulario de inicio de sesión está protegido contra solicitudes falsificadas, como todos los formularios (ejemplo 21);
    • líneas 40–45: el proceso de inicio de sesión. Si falla, el formulario se vuelve a mostrar con el nombre de usuario ingresado y un mensaje deliberadamente vago: decir «nombre de usuario desconocido» revelaría a un atacante qué nombres de usuario existen;
    • Líneas 49–54: si tiene éxito, el token se almacena en una cookie y el usuario es redirigido a la página protegida (patrón PRG). La cookie es [httpOnly]: el [JavaScript] de la página no puede leerla, lo que protege el token contra la inyección de scripts (XSS); es [SameSite=Lax]: el navegador no la envía con una solicitud POST proveniente de otro sitio, lo que protege la aplicación contra ataques CSRF; su fecha de expiración ([withExpires], aquí un número de segundos desde 1970) es la misma que la del token. En producción, con HTTPS, se agregaría [withSecure(true)]: la cookie nunca se enviaría a través de una conexión sin cifrar;
    • Líneas 59–68: cerrar sesión elimina la cookie ([clearCookie]). Es una acción POST, protegida por un token anti-CSRF: un simple enlace a [/logout], colocado en otro sitio o dentro de una imagen, no puede cerrar la sesión del usuario sin que este lo sepa. Cabe señalar una limitación de los tokens: el token en sí sigue siendo válido hasta que expira. Alguien que haya hecho una copia podría seguir usándolo. Por eso su duración de vida es limitada.

// src/Security/CaptchaService.php: los CAPTCHA pendientes, conservados por el servidor,

namespace App\Security;

use Psr\Cache\CacheItemPoolInterface;

class CaptchaService
{
    // la duración de un CAPTCHA, en segundos
    private const LIFETIME = 600;

    public function __construct(private CacheItemPoolInterface $cache)
    {
    }

    public function generate(): Captcha
    {
        $text = CaptchaDrawing::randomText(5);
        // un identificador aleatorio, imposible de adivinar: 12 bytes generados por un
        // generador criptográfico (random_bytes), escritos en hexadecimal (bin2hex)
        $id = bin2hex(random_bytes(12));
        // la respuesta esperada, en el caché, durante 10 minutos (expiresAfter): el
        // caché la olvidará por sí mismo después
        $item = $this->cache->getItem("captcha.$id");
        $this->cache->save($item->set($text)->expiresAfter(self::LIFETIME));
        return new Captcha($id, CaptchaDrawing::svg($text));
    }

    // el CAPTCHA se CONSUME en todos los casos: una imagen se usa una sola vez
    public function check(?string $id, ?string $answer): bool
    {
        // un identificador mal formado no puede ser una clave del caché
        if ($id === null || ! ctype_xdigit($id) || $answer === null) {
            return false;
        }
        $item = $this->cache->getItem("captcha.$id");
        // deleteItem: la respuesta se elimina del caché, sea correcta o no
        $this->cache->deleteItem("captcha.$id");
        if (! $item->isHit()) {
            return false;    // identificador desconocido, o CAPTCHA expirado
        }
        // strcasecmp devuelve 0 para dos cadenas iguales, sin distinguir mayúsculas de minúsculas
        return strcasecmp($item->get(), trim($answer)) === 0;
    }
}

Para cada identificador, el servidor almacena la respuesta esperada en la caché (ejemplo 20) durante diez minutos: el método [expiresAfter] del elemento de caché establece su duración de vida en segundos. Transcurrido este tiempo, la caché lo descarta automáticamente. La página recibe solo el identificador y la imagen: la respuesta nunca sale del servidor;
    • líneas 32–46: la validación. El identificador proviene del cliente: primero verificamos que conste de dígitos hexadecimales ([ctype_xdigit]), ya que ciertos caracteres ([{}()/\@:]) están prohibidos en las claves de la caché, lo que lanzaría una excepción. El elemento se lee y luego se elimina de la caché ([deleteItem]): el CAPTCHA se consume en todos los casos, tenga éxito o no. Sin esto, un programa podría probar todas las respuestas posibles sobre la misma imagen. La comparación ignora las mayúsculas y minúsculas ([strcasecmp] devuelve 0 para dos cadenas iguales, sin importar si las letras son mayúsculas o minúsculas) y los espacios alrededor de la entrada ([trim]).

use App\Security\AuthService;
use App\Security\CaptchaService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\RateLimiter\RateLimiterFactoryInterface;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    // $loginLimiter: la fábrica del limitador [login] (véase config/packages/framework.yaml);
    // el nombre del parámetro lo designa
    public function __construct(
        private AuthService $auth,
        private CaptchaService $captchas,
        private RateLimiterFactoryInterface $loginLimiter,
    ) {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->loginPage();
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        $inputs = $request->getPayload();
        if (! $this->isCsrfTokenValid('login', $inputs->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $inputs->getString('login');
        // el limitador de ESTE cliente: la clave de su contador de fallos es su dirección IP
        $limiter = $this->loginLimiter->create($request->getClientIp());

        // 1. una dirección bloqueada ni siquiera se escucha; consume(0) consulta el
        // contador sin consumir nada
        $state = $limiter->consume(0);
        if ($state->getRemainingTokens() === 0) {
            $seconds = $state->getRetryAfter()->getTimestamp() - time();
            return $this->loginPage($login, "Too many attempts: try again in $seconds s.");
        }
        // 2. primero el CAPTCHA (barato), después la contraseña (bcrypt, costoso);
        // consume(): un fallo más
        if (! $this->captchas->check($inputs->getString('captchaId'), $inputs->getString('captcha'))) {
            $limiter->consume();
            return $this->loginPage($login, 'The image code is incorrect.');
        }
        $user = $this->auth->validate($login, $inputs->getString('password'));
        if ($user === null) {
            $limiter->consume();
            return $this->loginPage($login, 'Incorrect login or password.');
        }
        // un inicio de sesión exitoso borra los fallos
        $limiter->reset();
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // cada visualización del formulario construye un CAPTCHA NUEVO
    private function loginPage(?string $login = null, ?string $error = null): Response
    {
        return $this->render('auth/login.html.twig', ['login' => $login, 'error' => $error,
            'captcha' => $this->captchas->generate()]);
    }

Por lo tanto, un programa que ingrese un CAPTCHA incorrecto no activaría [bcrypt]. Cada fallo, ya sea del CAPTCHA o de la contraseña, consume un token ([consume()], que consume uno por defecto). Después del tercer fallo, no quedan tokens: la dirección queda bloqueada hasta el final de la ventana de 60 segundos, contada a partir del primer fallo;
    • línea 70: un inicio de sesión exitoso borra los intentos fallidos ([reset()]);
    • líneas 91–95: cada vez que se muestra el formulario, se genera un nuevo CAPTCHA, incluso después de un intento fallido.

    SecurityBundle también ofrece un límite de conexiones integrado (la opción de firewall [login_throttling] ), que se aplica a sus propios autenticadores de inicio de sesión ([form_login]...), no a nuestra acción. Para limitar el número de solicitudes de una ruta, usaríamos un limitador de la misma manera, ya sea dentro de la acción o en un listener de [kernel.request]. Elegimos contar únicamente los intentos fallidos, para no incomodar a un usuario que inicia sesión con normalidad.
